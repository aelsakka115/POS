# RFC-005: Engineering Workflow & Development Constitution

**Type:** RFC (Engineering Governance — Phase 2)
**Depends on:** Product Bible v1، RFC-001 → RFC-004
**Status:** Proposed → Pending Review
**Audience:** Claude Code، Lovable، GitHub Copilot، Lead Architect، وأي مطوّر بشري مستقبلي

---

## 1. Purpose and Scope

RFC-004 يُثبِّت **الشكل الصحيح للأشياء** (طبقات، حدود اعتماد، معايير كود). RFC-005 يُثبِّت **كيف يتحرك الشغل فعليًا** — من فكرة، لتنفيذ، لقرار، لتوثيق مُحدَّث. هذا الفرق حاسم: RFC-004 معياري (Normative عن الكود)، RFC-005 إجرائي (Procedural عن الأشخاص والـ Agents).

### 1.1 ما لا تحتويه هذه الوثيقة عمدًا

- أي تفاصيل تقنية قابلة للتنفيذ (اسم فرع، إعداد CI، محتوى PR Template) — هذه **Repository Artifacts** منفصلة، تُنشَأ بعد اعتماد هذا الـ RFC، ولا تُكرَّر هنا نصًا.
- أي معيار كود أو معمارية مذكور بالفعل في RFC-004 — يُشار إليه بالرقم، لا يُعاد شرحه.
- أي قرار عمل أو معماري ثابت — تلك في Product Bible وRFC-001→004.

### 1.2 لماذا هذه الوثيقة ضرورية رغم صغر حجمها

المشروع مُدار بالكامل تقريبًا عبر AI Agents متعددة (Claude Code، Lovable، Copilot) بجانب مطوّر بشري واحد أو عدد قليل. بلا بروتوكول تعاون صريح، كل Agent هيبني افتراضات مختلفة عن نفس النظام. هذا الـ RFC هو العقد الوحيد اللي بيضمن إن كل Agent (بشري أو AI) بيتحرك بنفس القواعد، حتى لو ما فيش تواصل مباشر بينهم.

## 2. AI Collaboration Protocol

### 2.1 الأدوار والمسؤوليات

| الدور | المسؤولية | لا يقرر |
|---|---|---|
| **Claude Code** | تنفيذ الـ Backend (الطبقات الأربع، RFC-004 §6) دومين دومين، حرفيًا حسب الـ Domain Document المعني | لا يُغيِّر أي Business Rule أو يخترع Event جديد بدون المرور بـ §6 (Engineering Decision Process) |
| **Lovable** | تنفيذ الـ Frontend (RFC-004 §7) مستهلكًا `packages/domain-contracts` كعقد وحيد مع الـ Backend | لا يفترض شكل API لم يُنشَر بعد في `domain-contracts` |
| **GitHub Copilot** | مساعدة Inline أثناء الصيانة اليومية للكود القائم بالفعل | لا يُستخدَم لبدء دومين جديد من الصفر — هذا دور Claude Code/Lovable |
| **Lead Architect** (بشري) | ملكية كل RFC وDomain Document؛ السلطة النهائية في §5 و§6 | — |
| **Product Owner** (نفس الشخص غالبًا، قبعة مختلفة) | قرارات العمل التي تمس Business Rules (نفس دور Phase 1 بالكامل) | — |

### 2.2 دورة الحياة المُصغَّرة لأي مهمة

```
Task تظهر → فحص Definition of Ready (§3.1)
    → لو غير جاهزة: توقف، ارجع لمصدر الغموض (Domain Document / RFC)
    → لو جاهزة: تنفيذ بواسطة الـ Agent المناسب (§2.1)
        → فحص Definition of Done (§3.2)
        → لو أثارت سؤالًا معماريًا جديدًا: Engineering Decision Process (§6)
        → لو أثارت حاجة لتغيير قاعدة عمل موثَّقة: Change Management Process (§5)
    → مراجعة → دمج
```

هذه الدورة **مفهومية**، لا تفرض أي أداة Git أو CI بعينها — التطبيق العملي منها (فروع، PRs، Pipelines) Repository Artifact منفصل.

### 2.3 قاعدة بدء الجلسة (Session Bootstrapping)

أي AI Agent يبدأ أي جلسة عمل **يقرأ `docs/` أولًا** (Product Bible → RFC-004) قبل كتابة أي كود — امتداد مباشر لـ RFC-004 §11 Rule 5، وليس قاعدة جديدة.

### 2.4 بروتوكول تسليم بين الـ Agents (Handoff)

التسليم بين Claude Code وLovable **يمر حصريًا عبر `packages/domain-contracts`** — لا افتراضات شفهية أو غير موثَّقة. لو Lovable احتاج شكل بيانات مش موجود في الـ Contracts بعد، هذا يعني الدومين المعني في الـ Backend لسه مش جاهز — التوقف هنا **Definition of Ready Failure** (§3.1)، مش سبب للتخمين.

### 2.5 حل التعارض بين مخرجات Agents مختلفة

لو مخرجات Agent اتعارضت مع مخرجات Agent تاني (مثال: افتراض Frontend لشكل API يخالف الـ Backend الفعلي)، **`domain-contracts` هو الحَكَم الوحيد** — أيًا كان يخالفه هو الخطأ، بغض النظر عن أي Agent أنتجه. لو التعارض ناتج عن غموض في الـ Contract نفسه، يتصعَّد لـ Engineering Decision Process (§6).

## 3. Definition of Ready / Definition of Done

بوابتان لأي مهمة — دخول وخروج. **المبادئ هنا فقط؛ القائمة التنفيذية (Checkboxes) تعيش في Repository Artifacts (PR/Issue Templates)، وليست مُكرَّرة نصًا هنا.**

### 3.1 Definition of Ready (بوابة الدخول)

مهمة **غير جاهزة للتنفيذ** إلا إذا:
- القسم المعني في الـ Domain Document موجود، مُجمَّد، وغير غامض بخصوص هذه المهمة تحديدًا.
- أي Event أو Capability ID مطلوب **موثَّق بالفعل** في RFC-002/003 — لا افتراض "هنضيفه أثناء التنفيذ".
- معايير القبول (Acceptance Criteria) مذكورة بوضوح، مُشتقة من Business Rules الموثَّقة، وليست تفسيرًا شخصيًا للـ Agent المنفِّذ.
- لو المهمة بتلمس أكتر من دومين، حدود المسؤولية بين الدومينز واضحة من RFC-001 (لا "هنكتشف أثناء التنفيذ").

**لو أي شرط غير مُستوفى → المهمة ترجع لمصدرها (Domain Document/RFC) قبل أي كود، مش تتنفَّذ بافتراض.**

### 3.2 Definition of Done (بوابة الخروج)

مهمة **غير مكتملة** إلا إذا:
- الكود يحترم Dependency Rules (RFC-004 §5) — لا استيراد مباشر عابر للدومين.
- Capability Gating مطبَّق لو الـ Endpoint/UI مرتبط بـ Capability ID من RFC-003.
- اختبارات موجودة تتماشى مع هرم RFC-004 §8.
- التوثيق مُحدَّث وفق Documentation Update Policy (§4) — لو المهمة غيّرت سلوكًا موثَّقًا.
- لا Business Rule اتغيّرت بدون المرور بـ Change Management Process (§5) أولًا.

## 4. Documentation Update Policy

يُفعِّل RFC-004 §11 Rule 9 عمليًا: **متى وكيف يتزامن الكود مع التوثيق الحي؟**

### 4.1 القاعدة الذهبية

**أي تغيير يمس Business Rule موثَّقة يجب أن يُحدِّث الـ Domain Document المعني في نفس وحدة العمل** — لا "هنحدث التوثيق لاحقًا". دَين توثيقي (Documentation Debt) على مستوى Business Rules ممنوع تمامًا.

### 4.2 الاستثناء الوحيد

تعديلات تقنية بحتة (Refactoring بالمعنى الدقيق من RFC-004 §9.1 — لا تغيير سلوك خارجي) **لا تتطلب** تحديث أي Domain Document، لأن لا شيء موثَّق تغيَّر أصلًا.

### 4.3 من يعتمد تحديث التوثيق

أي تحديث لـ Domain Document (حتى لو بسيط) يحتاج مراجعة **Lead Architect** — نفس سلطة اعتماد أي وثيقة في Phase 1. AI Agent **يقترح** التحديث، لا **يعتمده** بنفسه.

---

## 5. Change Management Process

التعديل الرسمي لأي وثيقة **مُجمَّدة بالفعل** (Product Bible، أي RFC، أي Domain Document، System Freeze v1). هذا مختلف عن §4 — هنا مش "زامن التوثيق مع الواقع"، هنا **"غيّر الواقع نفسه"**.

### 5.1 من يقترح

أي Agent (بشري أو AI) يمكنه اقتراح تعديل، لكن **لا ينفِّذه بنفسه**.

### 5.2 الدليل المطلوب

نفس صرامة الأسلوب المُتبَع طوال Phase 1: تحديد الفجوة بدقة، الأثر على الوثائق المرتبطة (Cross-Domain Ownership، مصفوفة الأحداث)، الحلول المقترحة مع Trade-offs — **لا تعديل "لأنه يبدو أفضل"**.

### 5.3 من يعتمد

**Lead Architect (Product Owner) حصريًا** — نفس السلطة اللي اعتمدت System Freeze v1 وكل RFC حتى الآن. لا AI Agent يملك سلطة اعتماد تعديل معماري أو تجاري بنفسه.

### 5.4 الأثر التتابعي

أي تعديل مُعتمَد يتطلب **نفس فحص الاتساق الشامل** المُطبَّق في كل تحديث سابق عبر هذا المشروع (تحديث RFC-001/002/003 المرتبطة، Master-System-Flow، أي Domain Document متأثر) — لا تعديل مُنعزل.

## 6. Engineering Decision Process

مختلف عن §5: هنا قرار **تنفيذي/معماري** يظهر أثناء العمل، **مش موجود أصلًا** في RFC-004 أو أي وثيقة سابقة (مثال: الفجوات M1-M3 المُكتشَفة أثناء مراجعة RFC-004).

### 6.1 عتبة القرار (متى نحتاج توثيقًا رسميًا)

| نوع القرار | المسار |
|---|---|
| تفصيل تنفيذي يومي صغير (تسمية متغيّر، تنظيم ملف داخلي) | يُنفَّذ مباشرة، بلا توثيق رسمي — يقع تحت معايير RFC-004 §8 القائمة بالفعل |
| قرار معماري يؤثر على أكثر من ملف/دومين، أو يُنشئ نمطًا سيُعاد استخدامه | يُوثَّق كـ **SA-ADR جديد** يُضاف لسجل RFC-004 §14، بنفس صيغته (الالتزام المعماري مقابل الآلية القابلة للتغيير) |
| قرار يمس Business Rule | **ليس هذا المسار** — يتحوَّل فورًا لـ Change Management Process (§5) |

### 6.2 من يقرر

AI Agent يقترح حلولًا (زي ما حصل مع كل فجوة اتكتشفت طوال هذا المشروع)، لكن **Lead Architect يقرر**. لا استثناء حتى لو القرار يبدو تقنيًا بحتًا.

### 6.3 القاعدة الحاكمة لأي AI Agent هنا

**لو في شك: توقف، اعرض الخيارات بالـ Trade-offs، انتظر القرار.** هذا امتداد مباشر لقاعدة "Stop and report" المُتبَعة بلا استثناء طوال Phase 1 وPhase 2 — القاعدة الوحيدة المُكرَّرة عمدًا في كل وثيقة من هذا المشروع، لأنها الأهم.
